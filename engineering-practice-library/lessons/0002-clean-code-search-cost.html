Lesson 02 · Design

Clean code lowers search cost

“Clean” is not a decorating style. It is code that lets a change stay local and lets a reader predict where behavior lives.

Design judgmentTypeScript exampleOne refactoring drill

Win for this lesson

You can identify the part of a design that makes a change expensive: ambiguous names, mixed responsibilities, or a wide interface.

Complexity is what leaks

A module earns its keep when it hides decisions. The consumer should need a small amount of information to use substantial behavior. This is why “small function” is not a sufficient goal: many tiny functions can expose more concepts, force more navigation, and increase the search space.

1

Names create an index

A precise domain name gives both humans and agents a reliable search term. eligibleRefund narrows the question; checkData widens it.

2

Cohesion localizes change

Code that changes for the same business reason should live together. If refund policy changes require edits in UI helpers, database utilities, and a generic service, the module boundary is lying.

3

Interfaces ration knowledge

A narrow interface prevents callers from depending on internal sequencing, storage, or incidental data. Fewer legal interactions mean fewer ways an implementation can contradict itself.

Mixed policy, storage, and presentation

async function processRefund(order, db, mailer) {
  const days = (Date.now() - order.paidAt) / 86_400_000;
  if (days <= 30 && order.status !== "refunded") {
    await db.query("UPDATE orders SET status='refunded' WHERE id=?", [order.id]);
    await mailer.send(order.email, `Refunded ${order.total}`);
    return { color: "green", label: "Refund complete" };
  }
  return { color: "red", label: "Refund rejected" };
}

To change the refund window, a reader must pass through time math, storage syntax, email text, and UI styling. An agent sees the same enlarged reasoning surface.

Policy is explicit; effects sit behind ports

type RefundDecision =
  | { approved: true }
  | { approved: false; reason: "expired" | "already-refunded" };

function decideRefund(order: Order, today: Date): RefundDecision {
  if (order.status === "refunded") return { approved: false, reason: "already-refunded" };
  if (daysBetween(order.paidAt, today) > 30) return { approved: false, reason: "expired" };
  return { approved: true };
}

This is not automatically “better” because it is shorter. It is better if refund-policy changes now stay in one place, the decision is easy to test, and infrastructure can vary without contaminating the rule.

Rules are hypotheses, not scripture

Method length, class size, and complexity thresholds are signals. Robert Martin favors very small functions; John Ousterhout argues that over-decomposition can create shallow modules and navigation cost. Ask which design hides more complexity and localizes the next likely change.

Refactoring drill

For the first example, name the three independent reasons to change. Then choose one boundary you would create first. Do not refactor everything.

  1. Circle the business decision.
  2. Underline the side effects.
  3. Box the presentation decision.
  4. Extract only the boundary that enables the next test.

Retrieval check

A 600-line “billing helpers” file changes for pricing, invoicing, tax, and payment retries. What is the strongest first split?
