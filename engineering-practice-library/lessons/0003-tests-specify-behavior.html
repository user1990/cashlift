Lesson 03 · Behavior

Tests are executable decisions

A useful test does more than exercise code. It records what the system promises at a boundary someone cares about.

Story slicingGherkinUnit + QA layers

Win for this lesson

You can turn one human story into an observable acceptance example, a focused unit test, and a human-oriented QA procedure.

Start with the decision, not the interface

“Add a refund button” is a solution fragment. “A support agent can refund an eligible order and immediately see the final status” names the actor, capability, rule, and observable outcome. That is enough structure for an agent to implement while leaving design choices open.

1. Acceptance example: shared meaning

Feature: Refund a paid order
  Rule: Paid orders remain refundable for 30 days

  Scenario: Refund on the final eligible day
    Given a paid order is exactly 30 days old
    When a support agent refunds the order
    Then the order is shown as refunded
    And one refund is submitted for the paid amount

Given establishes context, When names the event, and Then states an externally observable result. The example chooses the boundary day because that is where an implementation error is likely.

2. Unit test: isolate the business rule

it("approves a refund on day 30", () => {
  const order = paidOrder({ ageInDays: 30 });

  expect(decideRefund(order)).toEqual({ approved: true });
});

it("rejects a refund after day 30", () => {
  const order = paidOrder({ ageInDays: 31 });

  expect(decideRefund(order)).toEqual({ approved: false, reason: "expired" });
});

The unit test makes the boundary cheap to exercise. It should not prove that the UI wires everything together.

3. QA procedure: prove the assembled path

  1. Open a seeded order paid exactly 30 days ago.
  2. Choose Refund and confirm the paid amount.
  3. Verify that the page shows Refunded.
  4. Reload and verify the status persists.
  5. Inspect the payment sandbox and verify one refund, not two.

This is written from the operator’s point of view. It can begin as a manual check and later become an end-to-end script if the path is stable and valuable.

Gherkin is not automatically good specification

When I click button #refund couples the scenario to the interface. When a support agent refunds the order names intent. Use Gherkin only when concrete examples improve shared understanding; plain tables or tests may be clearer for technical rules.

Three-layer exercise

Choose one small story. Write one boundary example, one unit-level rule, and three QA steps. Keep each layer responsible for different evidence.
