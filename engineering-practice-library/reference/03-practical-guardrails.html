Universal wrapperStart any task with the minimum contract

Start a real task with this short wrapper, then add only the relevant modules below.

TASK CONTRACT

Goal: [observable result]
Preserve: [behavior/files/APIs/accessibility/unrelated work]
Prohibited: [push/deploy/publish/contact/etc.]
State: prove checkout, branch, commit, dirty files, runtime, route, and baseline first.
Diagnosis: reproduce and test hypotheses before choosing implementation.
Done: report synthetic checks, independent behavior, final diff review, and limitations.
Handoff: record decisions, rejected alternatives, risks, and the safest next step.

Part I · Recurring anti-patterns repaired

Expand a case when you recognize the failure mode.

1. Diagnose before prescribingUse when a solution is suggested before evidence

Situation: You know the visual fix you want, but not the mechanism.

Bad: Make the drawer slide from the right and feel smoother.

REPAIR THIS REQUEST

First reproduce the drawer issue. Report actual versus expected geometry, then test at least two hypotheses covering layout, transform origin, scroll state, or sequencing. Recommend the smallest mechanism change only after the evidence.

Proof: reproduction steps, measured geometry, hypotheses tested, and a cause/fix explanation appear before edits.

2. Add independent reviewUse when the implementer would review its own assumptions

Situation: The same agent implements, tests its own assumptions, and declares success.

INDEPENDENT REVIEW

After implementation, assign a separate reviewer who did not make the change. Ask it to challenge assumptions, inspect accessibility and state conflicts, and rank regressions by severity. The implementer must reconcile the report before claiming completion.

Proof: reviewer identity/role, independent findings, rejected or accepted risks, and the integrator’s decision.

3. Prove preview identityUse when a responding browser may be stale or mismatched

Situation: A browser responds, but the route may come from another checkout or server.

PREVIEW IDENTITY

Prove the chain: target checkout → server working directory and command → browser URL and route. Report branch, commit, dirty files, runtime, and the process serving the port. If any identity is uncertain, stop; do not use the preview as evidence.

Proof: matching checkout/commit, server cwd/command, URL/route, and a baseline screenshot or behavior from that exact chain.

4. Reset the visual loopUse after two visual attempts miss the target

Situation: Several “slower,” “higher,” or “more polished” tweaks have missed.

RESET THE VISUAL LOOP

Stop editing after two misses. Restate invariant geometry, entry and exit states, timing, focus, scroll, reduced-motion behavior, and the exact screenshots or measurements that will prove it. Propose one consolidated change and wait for approval.

Proof: one written contract replaces the sequence of micro-corrections; both settled states are verified.

5. Write the handoffUse when a task may resume later

Situation: Tomorrow’s agent would need to reread the whole conversation.

WRITE THE HANDOFF

Record the objective, selected approach, rejected alternatives and reasons, changed surfaces, verification, unresolved risks, remaining decision, external approvals, and safest next action. Reference large existing artifacts instead of copying them.

Proof: a compact handoff exists at a durable project location and another agent can resume without transcript archaeology.

6. Preserve the delegation scorecardUse when multiple agents contribute evidence

Situation: You ask for many agents but cannot tell who concluded what.

DELEGATION SCORECARD

For each agent record: objective, context, scope, exclusions, write policy, return schema, acceptance criteria, stop condition, and owner. Preserve each report. The main agent must reconcile reports, state rejected alternatives, and name the final integrator.

Proof: role outputs and a decision scorecard survive, rather than only a vague summary.

7. Install a project baselineUse when a repository lacks reliable agent instructions

Situation: One repository has excellent instructions; another has none.

PROJECT BASELINE

Before risky work, load or propose the smallest root-level contract covering state inspection, scope preservation, acceptance, independent verification, external-action boundaries, and handoff. Keep project-specific details in task guidance.

Proof: the agent names the contract it loaded or flags its absence before mutation.

Part II · Strengths to preserve deliberately

Expand a case when you want to protect a good habit from being optimized away.

1. Name the outcomeMake “done” observable instead of subjective
OUTCOME

State the observable result, not a vague quality goal. Example: “At 390px, the mobile drawer opens from the trigger, traps focus, closes with Escape, and leaves the page scroll position unchanged.”

Proof: completion can be checked from behavior or measurement without asking what “better” means.

2. Preserve boundariesPrevent scope drift and accidental redesign
PRESERVE

Preserve existing copy, route contracts, keyboard behavior, accessibility semantics, responsive shell, and unrelated dirty work. Do not add dependencies or redesign adjacent surfaces.

Proof: the final diff and focused checks show the constraints survived.

3. Ground claims in artifactsUse screenshots, DOM, routes, and source as evidence
GROUNDING ARTIFACTS

Use the supplied screenshot, DOM state, route, structured data, and source file as evidence. Name each artifact and explain what claim it supports. Do not infer from a stale or unrelated preview.

Proof: every important recommendation points to an inspectable artifact.

4. Gate visual decisionsKeep exploration separate from production selection
SELECTION GATE

Produce exactly three labeled visual directions. Compare them against the stated contract. Do not apply a production branding or design choice until I select one direction.

Proof: options, criteria, and the selection decision are visible; exploration is not silently shipped.

5. Define acceptanceMake another person’s pass/fail result repeatable
ACCEPTANCE

Define expected DOM/state/visual outcomes before editing. Include viewport, interaction sequence, accessibility state, and what would falsify completion.

Proof: another person can run the checks and reach the same pass/fail result.

6. Use three proof channelsSeparate build, behavior, and diff evidence
THREE CHANNELS

Run focused tests, typecheck/lint/build; independently exercise the rendered flow and inspect console/network; then review the final diff for scope and necessity. Report each channel separately.

Proof: a green build is not used as a substitute for browser behavior or diff review.

7. Isolate the workProtect unrelated changes with branches and worktrees
ISOLATION

Use a fresh intended worktree when isolation is required. Before and after, list worktrees and dirty files. Do not reset, clean, or overwrite unrelated work.

Proof: unrelated changes remain intact and the target worktree is identifiable.

8. Challenge the modelChange the cause model, not only the visual value
CHALLENGE THE MODEL

If the result misses, do not only tune values. Explain which assumption failed, what evidence contradicts it, and which model or mechanism should replace it.

Proof: the next attempt changes the causal model when the evidence requires it.

9. Keep authority explicitStop before spending, publishing, deploying, or contacting
AUTHORITY

Local inspection and edits are allowed. Push, PR creation, deployment, publishing, spending, signup, messaging, uploads, and external contact require separate explicit authorization.

Proof: the agent stops before the side effect and shows destination, payload, scope, and rollback.

10. Capture durable evidenceLeave a restart point for the next session
DURABLE CAPTURE

End with a compact handoff, evidence ledger, build log, decision record, or definition of done when the task may resume. Link existing artifacts; do not leave important reasoning only in chat.

Proof: the next session has a restart point and known uncertainty.

Part III · Rules turned into daily moves

Expand a rule when you need the exact prompt line and its failure signal.

1. State before change

Prompt: Prove checkout, branch, commit, dirty files, runtime, route, and baseline before editing.

Failure signal: Agent edits before a baseline report.

2. Diagnose before prescribe

Prompt: Reproduce, state actual/expected, test competing hypotheses, then choose the smallest mechanism.

Failure signal: Solution appears before reproduction.

3. One task, one owner, explicit boundaries

Prompt: Name the integrator, in-scope surfaces, exclusions, and write authority.

Failure signal: Two agents mutate the same surface or nobody owns reconciliation.

4. Delegate bounded work with a return schema

Prompt: Return findings, evidence, risks, recommendation, and stop status in this schema.

Failure signal: “Here is some help” with no independently usable output.

5. Every completion needs independent proof

Prompt: Separate synthetic checks, independent behavior, and final diff review.

Failure signal: “Tests pass” is the only evidence.

6. Two misses trigger a contract rewrite

Prompt: After two misses, stop editing and rewrite invariants before another mutation.

Failure signal: Third micro-patch changes one value only.

7. Review the final diff, not only the rendered result

Prompt: Explain why each changed file is necessary and confirm no unrelated files changed.

Failure signal: Beautiful preview hides scope drift or accidental files.

8. Capture decisions before context disappears

Prompt: Record selected approach, rejected alternatives, evidence, risks, and next step.

Failure signal: Tomorrow’s work begins with “what did we decide?”

9. Worktree cleanup is part of completion

Prompt: List residue, stale servers, temporary artifacts, and safe cleanup actions; do not delete without authority.

Failure signal: Future work starts amid ambiguous sibling worktrees or ports.

10. External actions need separate authorization

Prompt: Stop before push, PR, deploy, publish, upload, message, or contact; show destination and payload first.

Failure signal: Approval is requested after the side effect.

One practical prompt that combines the system

Build the requested Spotify-like UI change, but follow this workflow:

1. STATE: prove target checkout, branch, commit, dirty files, runtime, server cwd/command, route, viewport, and baseline screenshot.
2. DIAGNOSE: reproduce the issue, state actual versus expected, and test at least two plausible causes.
3. PRESERVE: keep existing copy, accessibility, route/API contracts, responsive shell, design tokens, and unrelated work.
4. DELEGATE: if useful, assign separate analysis, adversarial review, and verification-design roles. No overlapping writes; return reports in a named schema.
5. IMPLEMENT: choose the smallest convention-matching change. Use near-black surfaces, functional green only, pill/circle geometry, compact type, and content-first color.
6. STOP: after two misses, rewrite the visual contract before editing again.
7. VERIFY: run focused checks, independently exercise the rendered route, inspect console/network, and review the final diff.
8. HAND OFF: record decisions, rejected alternatives, evidence, risks, residue, and the safest next step.
9. AUTHORITY: do not push, create a PR, deploy, publish, upload, or contact anyone without separate explicit approval.

Return a short report for each phase. Do not claim completion if any required phase is missing.
