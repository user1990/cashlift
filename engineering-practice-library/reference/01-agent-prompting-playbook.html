Reliable agent prompting

The central lesson from the audit: the prompting is already strong. The biggest gains now come from tightening the workflow around state, diagnosis, delegation, verification, and durable capture.

How to use this reference

Use the rules as compact principles, the “before” examples as anti-patterns, the “after” examples as good prompts, and the contracts as copy/paste gates. The audit’s numbers are retained because they identify leverage, not because they are universal benchmarks.

1. Establish the real working state before editing

Audit signal: latest branch, fresh worktree, live preview, or current master were often requested; stale previews, wrong checkouts, dirty primary branches, and leftover experimental state were repeatedly caught. Agent-state modeling was applied 8 of 10 times; inspect-before-edit 5 of 10.

Why: an excellent fix in the wrong checkout is still a failure. The artifact review found 18 sibling worktrees, four with residue, and mixed uncommitted work in primary checkouts.

Better pattern: make state discovery mandatory. Prove current directory; branch and commit; dirty files; runtime/version; running server and route; and baseline behavior.

Before · weak
Give live preview on latest master.

Problem: “latest” and “live” do not prove checkout identity, server identity, or baseline behavior.

After · good
Before editing, report:

1. Current directory, branch, commit, and dirty files.
2. Whether this is the intended checkout.
3. Runtime and package-manager versions.
4. The exact route or command used for the baseline.
5. Any existing implementation of the behavior.

Do not edit until the baseline is confirmed. If the checkout is stale, dirty in a conflicting way, or different from the requested branch, stop and explain the mismatch.

Reusable rule: No mutation before the agent proves which state it is mutating.

STATE GATE

Before making any change:

- inspect the current checkout and branch
- inspect dirty/untracked files
- inspect the current commit
- verify runtime and dependency state
- reproduce the current behavior
- identify the exact files and route involved

Return a short baseline report first. Do not edit until the state is confirmed.

2. Diagnose before prescribing the implementation

Audit signal: preferred visual or technical solutions were often provided immediately. Problem understanding was applied 5 of 9 times; root-cause orientation only 3 of 6. Repairs sometimes began from implementation prescriptions before reproduction or a falsifiable hypothesis.

Why: a prescribed solution narrows the agent too early and encourages symptom patches, especially in animation, layout, and state management.

Better pattern: separate observed symptom, expected behavior, reproduction, competing hypotheses, evidence, chosen mechanism, and implementation.

Before · symptom prescription
Make the drawer slide from the right and feel smoother.

Problem: the request names a mechanism and a vague quality word before identifying the failure.

After · diagnosis first
The observed problem is that the drawer starts from the wrong vertical position and appears to jump.

First:

- reproduce the behavior
- capture actual versus expected geometry
- inspect whether the cause is layout, transform origin, scroll state, or sequencing
- state at least two plausible hypotheses
- test the hypotheses before editing

Only then recommend the smallest mechanism change.

Reusable rule: Describe the failure and acceptance condition before describing the implementation.

DIAGNOSIS GATE

Do not start with implementation.

1. Reproduce the failure.
2. State actual behavior and expected behavior.
3. Identify the likely mechanism.
4. List competing hypotheses.
5. Test the hypotheses using the available evidence.
6. Explain why the chosen fix addresses the cause rather than the symptom.
7. Then implement the smallest fix.

3. Delegate deliberately, not merely when work is available

Audit signal: only 1 of 6 delegation opportunities was clearly applied. Delegation appeared in two sampled episodes, involving five child agents total, and was research-focused. No sampled implementation episode used an independent implementation reviewer. Agent brief quality, parallelism hygiene, and result integration were unmeasured because there were too few qualifying cases.

Why: the research fan-out is already known. The missing leverage is structured delegation for implementation review, risk analysis, and independent verification.

The company-building prompt was strong: autonomy, guardrails, evidence requirements, adversarial review, and completeness checks were specified. But the resulting artifacts preserved only summarized roles, not the actual delegation tree or scorecards.

Delegate only when work has: separable ownership; an independently verifiable output; a clear boundary; a defined return format; a stop condition; and a named integrator.

Before · vague fan-out
Use multiple agents aggressively and verify the result.

Problem: no ownership, non-overlap, write policy, output schema, or integration rule.

After · bounded workstreams
Delegate three independent workstreams:

Agent A — implementation analysis
- inspect the current mechanism
- propose the smallest safe change
- do not edit files
- return findings and exact evidence

Agent B — adversarial review
- look for regressions, accessibility problems, and state conflicts
- challenge Agent A’s assumptions
- do not edit files
- return risks ranked by severity

Agent C — verification design
- define the tests and browser checks that would independently confirm completion
- identify what would falsify the proposed fix

Main agent:
- reconcile all three reports
- choose one approach
- explain rejected alternatives
- implement only after reconciliation

Reusable rule: Delegate bounded decisions and evidence gathering, not vague “help.”

DELEGATION CONTRACT

Use subagents only for separable work.

For every delegated unit, specify:

- objective
- non-inheritable context
- files or surfaces in scope
- explicit exclusions
- whether writes are allowed
- required return format
- acceptance criteria
- stop condition
- owner responsible for integration

No delegated result is accepted without reconciliation into one final decision.

4. Make verification independent from the work that produced the claim

Audit signal: falsifiable acceptance was strong at 11 of 11; evidence injection was strong at 9 of 11; verification closure weaker at 7 of 11. Explicit diff review was applied only 1 of 3 times. Human browser review repeatedly caught issues that builds and DOM checks did not close.

Why: a build proves code builds, not that intended behavior is correct. A test written by the same implementation path can miss the same assumption.

Use three separate checks: synthetic verification (tests, typecheck, lint, build); independent behavioral verification (browser, API, data, or external observation); and human/diff review (inspect what changed and why).

Before · incomplete closure
Run the tests and tell me if it is done.

Problem: test passage is treated as user-visible correctness.

After · three channels
Completion requires all three:

1. Synthetic:
   - focused tests
   - typecheck
   - lint
   - production build

2. Independent behavior:
   - exercise the changed flow in the rendered browser
   - verify the expected state before and after interaction
   - inspect console and network output

3. Review:
   - inspect the final diff
   - confirm no unrelated files changed
   - explain why each changed file is necessary

Do not claim completion if any one of these is missing.

Reusable rule: Acceptance must use a channel that did not produce the original claim.

VERIFICATION CONTRACT

For every completion claim, report:

- expected result
- command or measurement used
- independent behavioral check
- final diff review
- remaining limitations

Separate “the command passed” from “the user-visible behavior is correct.”

5. Compress repeated visual feedback into a contract

Audit signal: context economy was generally strong at 9 of 11, but long visual loops repeated constraints and introduced large references late. The audit found repeated micro-corrections and churn before strategic resets. Recovery was strong overall, but not always early.

Why: repeated small corrections make the agent reconstruct design intent repeatedly, so it optimizes the latest sentence instead of the complete interaction contract.

After two failed iterations, stop editing and rewrite: invariant geometry; entry state; exit state; timing; focus behavior; scroll behavior; reduced-motion behavior; acceptance screenshots or measurements.

Before · micro-patch
Still too fast. Make it slower.

Problem: it changes a number without restating the motion contract or testing which invariant failed.

After · consolidated motion contract
Stop incremental tuning and summarize the motion contract:

- component begins aligned to the trigger
- panel travels the full available distance
- content does not jump vertically
- opening and closing use the same duration
- search opens only after the previous panel is closed
- reduced motion removes translation
- final proof must show both open and close states

Then propose one consolidated change.

Reusable rule: Two failed iterations trigger a contract rewrite, not another micro-patch.

ITERATION STOP RULE

If two consecutive attempts miss the target:

1. stop editing
2. summarize actual versus expected behavior
3. list all invariants
4. identify which prior assumptions failed
5. propose one consolidated approach
6. wait for approval before another mutation

6. Turn decisions into durable artifacts

Audit signal: durable memory and provenance was applied 7 of 11 times. Commits, handoffs, build logs, evidence ledgers, and definitions of done already exist, but important visual decisions sometimes remain in temporary worktrees or transcript history. Delegated outputs are sometimes summarized without a preserved scorecard or handoff tree.

Why: a future agent should not need to reconstruct why a direction was chosen from a long conversation.

Capture at the end of a meaningful task: goal; selected approach; rejected alternatives; changed files; verification; unresolved risks; next safe step; external actions still requiring approval.

Before · non-durable
The selected version is better. Continue tomorrow.

Problem: “better” has no preserved decision, evidence, risk, or restart point.

After · handoff
Write a durable handoff containing:

- final objective
- selected design or mechanism
- rejected alternatives and reasons
- exact changed surfaces
- verification already completed
- known failures or unverified areas
- remaining decision
- safest next action

Do not duplicate large source material; reference existing artifacts instead.

Reusable rule: Every task that may be resumed needs a compact decision record.

HANDOFF CONTRACT

Before ending, create a concise handoff with:

- objective
- current state
- decisions made
- rejected alternatives
- files or surfaces changed
- verification and results
- blockers and uncertainty
- external actions still requiring approval
- safest next step

Keep it compact and reference existing artifacts instead of copying them.

7. Standardize the minimum agent contract across projects

Audit signal: some folders have rich routing, safety, testing, and worktree guidance; others have short notes or none. Instruction maturity is uneven, so the strongest safeguards do not automatically transfer to every project.

Why: an agent entering a sparse project has less protection against wrong-state edits, weak verification, or scope drift.

Keep a small universal project contract: inspect before edit; preserve unrelated changes; classify the task; state acceptance; verify independently; do not push or publish without explicit authority; leave a handoff.

Before · insufficient
Follow the project instructions.

Problem: it delegates safety to instructions that may be absent or incomplete.

After · project minimum
Project minimum contract:

- inspect current state before mutation
- preserve unrelated dirty work
- identify task type and affected surface
- state acceptance before editing
- use the smallest convention-matching change
- run independent verification
- do not push, publish, or contact anyone without explicit authorization
- leave a durable handoff for unfinished work

Reusable rule: Put only universal, trigger-critical rules in the project root; keep deeper guidance task-specific.

PROJECT BASELINE

Before starting, load the project’s minimum agent contract:

- state inspection
- scope and preservation rules
- acceptance requirements
- verification commands
- external-action boundaries
- handoff requirements

If the project lacks one, propose the smallest root-level contract before making a risky change.

8. Move external-action approval to the front

Audit signal: constraint precision was strong at 10 of 12; decision rights very strong at 10 of 10. The company-building prompt prohibited publication, spending, signup, messaging, and deployment. In some workflows, push or PR creation happened before a later confirmation step.

Why: later approval is weaker than an upfront authorization boundary; the agent can cross the line while packaging work.

Separate: local edits; local commits; branch push; pull request creation; deployment; external communication.

Before · late boundary
Create the PR when done, then ask me if I want it updated.

Problem: PR creation has already crossed the external boundary before consent.

After · upfront authority
Authority boundary:

- local edits: allowed
- local commit: allowed
- push: not allowed yet
- PR creation: not allowed yet
- deployment or external communication: prohibited

Before any remote action, stop and show:
- exact action
- destination
- files or data included
- why it is needed
- rollback or recovery path

Reusable rule: Treat every external side effect as a separate permission, not as part of “finish the task.”

EXTERNAL ACTION GATE

You may inspect and edit locally.

You may not push, create or update a remote review, deploy, publish, send messages, upload files, or contact external services unless I explicitly authorize that exact action.

Before asking, show the destination, payload, scope, and rollback path.

Recurring anti-patterns

  • Prescribing implementation before reproduction and mechanism analysis.
  • Letting the agent remain in one implementation/review loop without an independent reviewer.
  • Allowing stale previews, dirty worktrees, or wrong checkouts to become a source of rework.
  • Continuing visual micro-tuning after the interaction contract is already unclear.
  • Leaving important decisions in temporary worktrees or transcript history.
  • Using strong orchestration prompts without preserving the delegation tree, role outputs, or scorecard.
  • Applying the strongest agent rules unevenly across projects.

Strengths to preserve

  • Usually stating a concrete outcome.
  • Providing strong constraints, preservation rules, and non-goals.
  • Anchoring work with real artifacts, screenshots, browser state, structured data, and source material.
  • Using explicit selection gates before many high-judgment visual changes.
  • Requesting checkable acceptance conditions.
  • Using layered testing, builds, browser verification, and human review.
  • Protecting unrelated work with branches and worktrees.
  • Rejecting weak directions and changing the model.
  • Limiting spending, publication, deployment, and external contact.
  • Creating durable artifacts more often than most agent users.

Rules to remember

  1. State before change.
  2. Diagnose before prescribe.
  3. One task, one owner, explicit boundaries.
  4. Delegate bounded work with a return schema.
  5. Every completion needs independent proof.
  6. Two failed iterations trigger a contract rewrite.
  7. Review the final diff, not only the rendered result.
  8. Capture decisions before the context disappears.
  9. Treat worktree cleanup as part of task completion.
  10. External actions require separate explicit authorization.

Full start checklist

TASK START CHECKLIST

Goal:
What observable result do I want?

Done:
What exact evidence will prove completion?

Preserve:
What behavior, files, APIs, accessibility, or unrelated work must remain unchanged?

Do not:
What actions are prohibited?

State:
What checkout, branch, commit, runtime, and baseline behavior are active?

Diagnosis:
What is the actual failure or ambiguity?
What hypotheses should be tested before editing?

Delegation:
Does this split into independently verifiable units?
Who owns integration?
Who independently reviews the result?

Verification:
What synthetic checks, behavioral checks, and diff review are required?

Recovery:
What is the stop condition?
What becomes a durable handoff if the task pauses?

External actions:
Which actions, if any, require a separate approval?
