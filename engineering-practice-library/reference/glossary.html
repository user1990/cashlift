Course glossary

Use these definitions consistently when specifying work, interpreting checks, and discussing tradeoffs.

A–C

Acceptance criterion
A business rule or condition that must hold for a story to be accepted. A concrete example illustrates it; the two are not synonyms.
Agent harness
The software around a model that supplies context, tools, permissions, an execution loop, and feedback.
Bottleneck
The pipeline step whose capacity sets system throughput. Speeding any other step creates inventory, not delivery. See pipeline constraint map.
Branch coverage
The proportion of control-flow outcomes executed by tests. It records execution, not assertion quality.
Characterization test
A test that records current observable behavior before risky refactoring, whether or not that behavior is ideal.
Cohesion
The degree to which code in a module belongs together because it serves one capability or reason to change.
Contract test
A check that a component or service honors an interface agreement at a boundary.
CRAP metric
An experimental score combining cyclomatic complexity and method coverage to highlight complex, poorly exercised code. Originally “Change Risk Analysis and Predictions”; later tools use variant expansions.
Cyclomatic complexity
The size of a basis set of linearly independent paths in a control-flow graph—not the total possible execution paths.

D–M

Deterministic check
A repeatable procedure that returns an observable result for the same inputs, such as a compiler, test, linter, or dependency rule.
Equivalent mutant
A mutation that does not change observable program behavior and therefore cannot be killed by any valid test.
Executable specification
A human-readable description connected to code that verifies its examples, such as well-written Gherkin scenarios.
Fitness function
An automated check that continuously evaluates an architectural or operational property.
Gherkin
Cucumber’s grammar for structuring concrete examples with keywords such as Feature, Rule, Given, When, and Then.
Information hiding
Designing a module so callers need not know the internal decisions most likely to change.
Invariant
A condition that must always hold at a defined boundary or state transition.
Inventory
Finished-looking work that has not passed the constraint: unreviewed diffs, unshipped builds, or unused MVPs. Visible progress is not throughput.
Killed mutant
An inserted fault that causes at least one test to fail, demonstrating that the suite distinguishes that change.
Mutation testing
Systematically inserting small faults and rerunning tests to evaluate the suite’s fault-detection sensitivity.

O–Z

Oracle
The mechanism that decides whether observed behavior is correct. Weak oracles let wrong results pass even when code is covered.
Port and adapter
A boundary pattern where core policy defines an interface (port) and infrastructure-specific code implements it (adapter).
QA procedure
A human-oriented sequence that exercises the assembled system at its real interface and names deterministic expected outcomes.
Ratchet
A policy that prevents quality from moving backward while gradually tightening a baseline, especially useful in legacy systems.
Refactoring
Changing internal structure to improve understandability or modification cost without changing observable behavior.
Statement coverage
The proportion of executable statements run by tests. It cannot prove that outputs were asserted or requirements are complete.
Surviving mutant
An inserted change that does not fail the suite; it may reveal a missing assertion, dead code, equivalent behavior, or a justified exception.
Test pyramid
A heuristic favoring many fast focused tests and fewer broad end-to-end tests; the useful shape depends on the system and risk.
Threshold career
A field where entry rungs thinned because low-complexity work is generated, while demand remains above a bar. Contrast with a ladder career that trains through grunt work.
Unit test
A fast test of a small behavioral unit through a stable boundary, isolated enough that failures are easy to diagnose.
