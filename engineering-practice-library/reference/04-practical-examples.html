Core gates · good/bad examples first

These are the primary prompt contracts. Learn these before the anti-pattern catalogue.

1. Confirm the right checkout before editing — STATE GATEProve which checkout and preview you are changing

Bad: Give live preview on latest master.

Good:

Before editing, report current directory, branch, commit, dirty files, intended checkout, runtime, package manager, exact route or command, and baseline behavior. Do not edit until the state is confirmed.

Proof: checkout → server → browser identity is explicit and matches.

2. Find the cause before changing code — DIAGNOSIS GATEFind the cause before prescribing implementation

Bad: Make the drawer slide from the right and feel smoother.

Good:

Reproduce the drawer issue. State actual versus expected behavior. Capture geometry and test layout, transform origin, scroll state, and sequencing as competing hypotheses. Recommend the smallest mechanism change only after evidence.

Proof: reproduction, hypotheses, evidence, and cause/fix reasoning appear before edits.

3. Give each agent one clear job — DELEGATION CONTRACTGive parallel agents bounded ownership

Bad: Use multiple agents aggressively and verify the result.

Good:

Agent A: implementation analysis, no writes. Agent B: adversarial accessibility and regression review, no writes. Agent C: independent verification design, no writes. Each returns objective, evidence, risks, recommendation, and stop status. Main agent owns reconciliation.

Proof: every role has a boundary, return schema, stop condition, and integrator.

4. Prove the result in three ways — VERIFICATION CONTRACTProve behavior through independent channels

Bad: Run the tests and tell me if it is done.

Good:

Completion requires focused tests/typecheck/lint/build, independent browser or API behavior, and final diff review. Report expected result, command or measurement, independent check, changed-file review, and limitations.

Proof: build health is reported separately from user-visible correctness.

5. ITERATION STOP RULEReplace micro-tuning with a contract rewrite

Bad: Still too fast. Make it slower.

Good:

After two misses, stop editing. Summarize actual versus expected behavior, list invariants, identify failed assumptions, rewrite the motion contract, and propose one consolidated approach before another mutation.

Proof: the next change addresses the contract, not only one value.

6. HANDOFF CONTRACTMake decisions recoverable tomorrow

Bad: The selected version is better. Continue tomorrow.

Good:

Write a handoff with objective, current state, selected approach, rejected alternatives and reasons, changed surfaces, verification, unresolved risks, remaining decision, approvals, and safest next action.

Proof: a new agent can resume without rereading the transcript.

7. PROJECT BASELINEInstall minimum safety rules in sparse projects

Bad: Follow the project instructions.

Good:

Before risky work, load the project contract for state inspection, preservation, acceptance, independent verification, external-action boundaries, and handoff. If missing, propose the smallest root-level contract before mutation.

Proof: the agent names the loaded contract or flags its absence.

8. EXTERNAL ACTION GATESeparate local completion from remote side effects

Bad: Create the PR when done, then ask me if I want it updated.

Good:

Local edits and verification are allowed. Push, PR creation, deployment, publishing, uploads, messages, and external contact are not allowed yet. Before asking, show destination, payload, scope, reason, and rollback.

Proof: authorization is requested before the side effect, not after it.

Recurring anti-patterns · practical avoidance

1. Prescribing before reproductionDrawer animation bug

Situation: A mobile drawer jumps when it opens.

Weak move: Change translateY to translateX and make it smoother.

Practical correction:

Reproduce the drawer at 390px. Capture its trigger position, panel geometry, scroll position, and focus state before and after opening. Test whether layout, transform origin, scroll locking, or sequencing causes the jump. Only then choose the smallest fix.

Proof: measured before/after geometry and a tested cause appear before implementation.

2. No independent reviewerSelf-reviewed UI change

Situation: One agent changes a mobile navigation component and says “tests pass.”

Weak move: The same agent decides the interaction, writes the test, and reviews the result.

Practical correction:

Ask an independent reviewer to inspect the changed navigation without trusting the implementer’s assumptions. Check keyboard focus, Escape handling, reduced motion, scroll locking, mobile widths, and state conflicts. Return risks ranked P0–P3 before completion.

Proof: a separate review report exists, and the integrator records which risks were fixed or accepted.

3. Trusting a stale previewWrong checkout or server

Situation: The browser shows a working page, but you are unsure which checkout produced it.

Weak move: The page loads, so the fix is verified.

Practical correction:

Before using the preview as evidence, print the target checkout, branch, commit, dirty files, server working directory, server command, port, browser URL, and route. Confirm that the browser behavior comes from that exact chain.

Proof: checkout → server → browser identity matches; otherwise verification is marked blocked.

4. Micro-tuning an unclear visual contract“Make it feel smoother” loop

Situation: A command palette has received several speed, offset, and easing tweaks but still feels wrong.

Weak move: Try 50ms slower and move it 4px up.

Practical correction:

Stop after two misses. Write the motion contract: trigger alignment, entry state, exit state, duration, focus target, scroll behavior, reduced-motion behavior, and screenshots for open/close. Propose one consolidated change before editing again.

Proof: the contract is stable and both open and close states pass without another micro-patch.

5. Leaving decisions in chatDesign choice cannot be resumed

Situation: Three logo directions were explored and the next session must continue the decision.

Weak move: Option B feels best. Continue tomorrow.

Practical correction:

Write a decision record: selected direction, rejected directions and reasons, optical adjustments, affected files, screenshots reviewed, unresolved risks, and the next safe action. Link the source images instead of copying the whole discussion.

Proof: another agent can resume the design decision from one durable file.

6. Delegating without a scorecardParallel research becomes noise

Situation: Three agents investigate a UI bug and return overlapping opinions.

Weak move: Use multiple agents and tell me what they find.

Practical correction:

Agent A: reproduce and measure; no writes. Agent B: adversarial accessibility and regression review; no writes. Agent C: design independent verification; no writes. Each returns evidence, risks, recommendation, and stop status. Main agent owns reconciliation.

Proof: each role has a bounded report and the final decision explains how conflicts were reconciled.

7. Uneven project rulesNew repository lacks safety defaults

Situation: One project has excellent agent instructions; a new project has none.

Weak move: Follow the project instructions.

Practical correction:

Before risky work, confirm the project contract covers state inspection, preservation, acceptance, independent verification, external-action boundaries, and handoff. If it does not exist, propose the smallest root-level contract before mutation.

Proof: the baseline is loaded or its absence is explicitly reported before edits.

Strengths to preserve · practical examples

1. Concrete outcomeTurn “improve UX” into a check

Situation: You want a mobile drawer to feel better.

Practical prompt:

At 390px, clicking the menu trigger opens the drawer aligned to the trigger, traps focus, closes with Escape, restores focus to the trigger, preserves scroll position, and removes translation under reduced motion.

Why preserve it: the agent can verify behavior instead of guessing what “better” means.

2. Constraints and non-goalsStop a local fix becoming a redesign

Situation: You are fixing a FAQ article route.

Practical prompt:

Preserve the existing slug contract, query parameter, canonical metadata, keyboard behavior, responsive shell, copy, and sitemap behavior. Do not redesign the help index or add a dependency.

Why preserve it: the requested change stays small and unrelated contracts remain safe.

3. Real artifacts as evidenceReplace intuition with inspectable facts

Situation: A preview looks different from the screenshot reference.

Practical prompt:

Use the exact screenshot, DOM snapshot, route, viewport, server cwd, and source component as evidence. For every visual recommendation, name the artifact that supports it. Mark claims based on stale or indirect evidence as unverified.

Why preserve it: disagreement becomes a question of evidence rather than taste alone.

4. Selection gates for visual workKeep exploration from silently shipping

Situation: You are exploring three Spotify-like logo or hero directions.

Practical prompt:

Generate exactly three labeled directions. Compare each against contrast, optical balance, functional green usage, responsive fit, and brand distinctiveness. Pause for my selection; do not replace the production asset during exploration.

Why preserve it: high-judgment choices stay reversible until explicitly selected.

5. Checkable acceptanceMake completion repeatable

Situation: You add category filters to the guardrail reference.

Practical prompt:

Acceptance: All shows 28 topics; Core shows 1; Anti-patterns shows 7; Strengths shows 10; Rules shows 10; search updates results immediately; empty results show a message; filter buttons expose aria-pressed; accordions and copy buttons still work.

Why preserve it: another person can verify the same contract without relying on your impression.

6. Layered verificationDo not confuse build health with behavior

Situation: You add an interactive filter to a static lesson.

Practical prompt:

Run JavaScript syntax checks and static link checks. Independently exercise category selection, search, empty results, accordion expansion, and code copying. Review the diff and confirm only the intended assets/pages changed.

Why preserve it: each evidence channel catches a different class of failure.

7. Branch and worktree isolationProtect unrelated active work

Situation: You need to experiment with a new header animation while the main checkout is dirty.

Practical prompt:

Use a fresh worktree from the intended base. Record its path, branch, commit, and dirty state. Do not reset or clean the primary checkout. At the end, report residue and safe cleanup options separately.

Why preserve it: experimentation cannot destroy work that was outside this task.

8. Reject weak directionsChange the model when evidence disagrees

Situation: Slowing an animation twice does not remove the perceived jump.

Practical prompt:

Do not tune duration again by default. Explain whether the evidence points to layout shift, transform origin, scroll locking, focus movement, or sequencing. Replace the failed timing hypothesis with the best-supported causal model.

Why preserve it: the workflow learns instead of repeating the same kind of patch.

9. Explicit authority limitsKeep local work separate from external effects

Situation: A local feature is complete and a pull request seems like the natural next step.

Practical prompt:

Local edits and local verification are allowed. Do not push, create a PR, deploy, publish, upload, spend money, send messages, or contact anyone. Before any remote action, stop and show destination, payload, scope, reason, and rollback.

Why preserve it: “finish the task” cannot silently become an external side effect.

10. Durable artifactsMake tomorrow’s restart cheap

Situation: A task pauses after implementation but before final review.

Practical prompt:

Before ending, write a compact handoff with objective, current state, changed files, decisions, rejected alternatives, verification, known limitations, remaining approval, and safest next step. Reference existing screenshots and logs.

Why preserve it: the next session starts from a decision record, not from memory reconstruction.

Rules to remember · practical application

1. State before changeProve the reality you will mutate

Situation: You are asked to fix a Help route and open a preview.

Practical prompt:

Before editing, report the checkout path, branch, commit, dirty files, runtime, server cwd/command, browser URL, route, and baseline behavior. Stop if any identity is uncertain.

Failure signal: The agent edits or cites a preview before returning the baseline report.

2. Diagnose before prescribeFind the cause before choosing the mechanism

Situation: A sidebar appears one pixel too low on mobile.

Practical prompt:

Reproduce the offset. State actual versus expected geometry. Test layout flow, transform origin, safe-area padding, and scroll state as competing hypotheses. Recommend the smallest fix only after evidence.

Failure signal: The first proposed CSS property appears before reproduction or hypothesis testing.

3. One task, one owner, explicit boundariesPrevent overlapping writes and lost decisions

Situation: Two agents are exploring a command palette and a third is reviewing it.

Practical prompt:

Agent A owns implementation analysis; Agent B owns adversarial review; Agent C owns verification design. No delegated writes. The main agent owns reconciliation and the final implementation decision.

Failure signal: Multiple agents edit the same component or no one owns the final decision.

4. Delegate bounded work with a return schemaMake parallel work independently useful

Situation: You want separate research on accessibility, animation, and browser verification.

Practical prompt:

Return exactly: objective, inspected surfaces, evidence, risks, recommendation, rejected alternatives, and stop status. Do not edit files. Stop when the requested evidence is complete.

Failure signal: The result is a vague opinion that cannot be reconciled or independently checked.

5. Every completion needs independent proofSeparate “passed” from “correct”

Situation: The build and tests pass for a new filter control.

Practical prompt:

Report focused checks separately from independent behavior. Exercise All, each category, search, empty results, accordion expansion, and copy. Then review the final diff and list limitations.

Failure signal: “Tests pass” is the only completion evidence.

6. Two misses trigger a contract rewriteStop repeating micro-patches

Situation: Two motion tweaks failed to fix a drawer jump.

Practical prompt:

Stop editing. Summarize actual versus expected behavior, list invariants, identify failed assumptions, rewrite the motion contract, and propose one consolidated approach before another mutation.

Failure signal: A third patch changes only duration, offset, or easing without changing the model.

7. Review the final diff, not only the rendered resultCatch scope drift behind a good preview

Situation: The new page looks correct in the browser.

Practical prompt:

Review the final diff. Explain why every changed file is necessary, confirm no unrelated files changed, check removed imports and assets, and compare the implementation with the requested scope.

Failure signal: The page looks right, but unrelated files, dependencies, or copy changed unnoticed.

8. Capture decisions before context disappearsMake the next session startable

Situation: You pause after selecting one of three visual directions.

Practical prompt:

Write the handoff now: selected direction, rejected options and reasons, exact files, evidence reviewed, unresolved risks, remaining decision, and safest next action.

Failure signal: The next session begins by reconstructing the decision from chat history.

9. Worktree cleanup is part of completionLeave the workspace unambiguous

Situation: A task used a temporary worktree and local server.

Practical prompt:

Before ending, list the worktree path, branch, dirty files, stale server/process, temporary artifacts, and safe cleanup options. Do not delete anything without explicit authority.

Failure signal: The next task cannot tell which checkout or port is authoritative.

10. External actions need separate authorizationStop before the side effect

Situation: Local implementation and verification are complete.

Practical prompt:

Do not push, create a PR, deploy, publish, upload, send messages, or contact anyone yet. Before any remote action, show the exact destination, payload, scope, reason, and rollback path.

Failure signal: The agent asks for approval after already creating the PR or sending the message.
