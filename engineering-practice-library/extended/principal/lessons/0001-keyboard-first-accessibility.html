Lesson 0001

Keyboard-first accessibility

Principal-level frontend work starts with one habit: before adding ARIA or polish, prove that the interface works from the keyboard.

Reference sheet

The one decision

If a native HTML element gives you the behavior and semantics you need, use it. MDN says native elements bring built-in keyboard accessibility, roles, and states; W3C's ARIA guidance says authors must provide keyboard behavior when they create ARIA widgets themselves.

Primary sources: MDN ARIA, W3C Using ARIA, W3C APG Keyboard Interface.

Why this matters

Keyboard users need a path

W3C APG frames keyboard UX around visible focus, predictable focus movement, Tab order between components, and expected movement inside composite widgets.

Focus is state

WCAG Focus Visible requires a visible keyboard focus indicator. If the user cannot see where focus is, they cannot reliably operate the page.

ARIA is not behavior

ARIA can describe meaning to assistive technology. It does not automatically add Enter, Space, Escape, arrow-key handling, or focus restoration.

Contrast is not optional

WCAG Contrast Minimum sets 4.5:1 for normal text and 3:1 for large text. Thin fonts and subtle colors can pass numerically but still read poorly.

Interview answer pattern

When asked about accessibility, answer like this:

  1. Start with semantic HTML.
  2. Test keyboard path before mouse polish.
  3. Keep focus visible and predictable.
  4. Add ARIA only for missing semantics.
  5. Verify with real browser behavior, then assistive tech when risk is high.

Practice: native or custom?

For each snippet, choose whether the safer Principal-level default is native or custom. The answer labels are intentionally equal length.

1. <div role="button" tabindex="0">Save</div>
2. <button type="button">Save</button>
3. <ul role="listbox">...arrow-key behavior...</ul>
Choose answers, then check.

Small real-world task

Open any app screen you use. Press Tab from the browser address bar until you reach the main action. Write down the first place where focus disappears, jumps unpredictably, or lands somewhere useless. That is the bug report.

Primary source to read

Read W3C APG's Developing a Keyboard Interface. Focus only on the introduction, visible focus, tab sequence, and movement inside components.
