Lesson 0002

Principal mindset: defaults across teams

A Principal Frontend Engineer does not win by owning every decision. They make important decisions easier, visible, and repeatable.

Sprint index

The useful distinction

Senior engineers often solve hard problems inside one team. Principal engineers reduce repeated problem-solving across teams by shaping defaults: data fetching, error states, feature boundaries, analytics, accessibility, performance budgets, and review standards.

Primary source: React: Thinking in React. Use it as a small model for decomposing UI and state before scaling that thinking to teams.

Example

Three teams show API errors differently: one toast, one blank screen, one raw backend message. The Principal move is not "build a shared toast." The better move is a standard error contract, reusable ErrorState, logging convention, and migration path for important routes.

Practice

Write three frontend defaults that would help Report, Checkout, and CMS/Marketing teams without removing their autonomy.

Write first, then check.

Good answer direction

"I would standardize decision boundaries before standardizing every component: data fetching, error states, form validation, analytics, accessibility, and shared UI ownership. Teams stay autonomous in feature logic, but they stop reinventing base patterns for the same recurring problems."
