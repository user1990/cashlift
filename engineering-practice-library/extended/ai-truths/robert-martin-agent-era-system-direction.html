Direct the system, not just the agent

A practical interpretation of the Robert C. Martin interview: preserve human judgment over architecture, quality, and customer outcomes while agents accelerate local implementation.

1. The thesis: the abstraction line rises

Martin's argument is simple: languages, frameworks, and machines change fast; software design principles above those details change much more slowly. AI moves more implementation work below the line. It does not remove the need to decide what the system is, how its parts depend on each other, or whether it solves the right problem.

Changes quickly

Implementation mechanics

Syntax, library APIs, code generation, boilerplate, and local transformations.

Stays durable

System structure

Modules, boundaries, dependency direction, information hiding, data flow, and failure behavior.

Human accountability

Judgment

Tradeoffs, long-term consequences, customer reality, and the evidence required to ship.

Staff-level translation: do not ask only “did the agent produce working code?” Ask “what system property changed, what must remain stable, and what evidence makes this safe to operate?”

2. The operating model: inspect the architecture delta

Martin describes deliberately avoiding code until a task is complete, then inspecting modules, functions, dependencies, and data flows. That is sensible only if it becomes a disciplined review surface—not blind trust.

Do not edit code yet. Produce an architecture-delta report.

1. Affected modules and their responsibilities
2. Allowed and forbidden dependency changes
3. Source-to-sink data flow
4. Happy path plus auth, validation, retry, concurrency, and partial-failure paths
5. Tests, telemetry, and rollback evidence needed for approval
6. Product assumptions that require a human decision

Tie every claim to a file, test, log, or explicit uncertainty.

3. Worked example: tenant-scoped invoice exports

Request: “Let workspace admins export filtered invoices to CSV.” The local coding task is easy; the system design task is not.

Weak delegation

“Build CSV export.”

  • May read another tenant's data.
  • May ignore active filter semantics.
  • May time out on large data sets.
  • May omit auditability and expiration.

Staff delegation

“Propose the smallest architecture delta for an async, tenant-scoped export. Preserve existing filter semantics; do not change invoice schema.”

  • Admin action creates a request.
  • Server validates membership and filters.
  • Worker produces private output.
  • Audit trail and expiring download close the loop.

Make these decisions before the agent touches code

DecisionConcrete choiceConstraint in the agent task
OwnershipBilling application service orchestrates exports.UI may request an export; it cannot bypass auth or create files.
ContractFilters and timezone are snapshotted at request time.Reuse the existing validated filter schema.
SecurityEvery query is tenant-scoped; only admins request/download.No raw ID lookup without workspace authorization.
ScaleLarge work runs asynchronously with a defined limit.No unbounded request-time CSV generation.
RecoveryJobs are idempotent; downloads expire.Show retry, cleanup, and duplicate-request behavior.

4. Clean code when agents write it

The transcript does not say quality is irrelevant. It shifts attention to function and module shape, names, argument counts, complexity, comments, and test coverage. Martin mentions a coverage-weighted complexity measure (“CRAP”) and an example threshold below six.

Do not cargo-cult the number. A complexity limit is only a useful signal when paired with real test quality, business criticality, and team conventions. A green metric is not proof the system is understandable.

Automate signals

  • Type checks and linting
  • Focused behavioral tests
  • Coverage where missing tests hide branching risk
  • Dependency or import-boundary checks
  • Diff-size and changed-file scope review

Keep human review for

  • Wrong ownership or boundary placement
  • Misleading abstraction or duplicate state
  • Unacceptable failure behavior
  • Product tradeoffs and customer friction
  • Whether the evidence proves the intended outcome
Prompt: make the agent close its own loop
Implement the bounded change. Before declaring success, run the agreed checks.

Then report only:
- changed responsibility and dependency edges;
- data flow and external side effects;
- tests and quality checks run, with results;
- known gaps or assumptions;
- the single highest-risk failure path still worth human review.

5. Design sense, context limits, and beginner fundamentals

Martin's view is that agents can critique a design when asked, yet do not reliably apply that critique while generating code. He also warns that long contexts can cause unreliable behavior. Treat both as failure modes to design around: bound tasks, preserve essential context as artifacts, and demand evidence.

For senior/staff engineers

Use agents to explore alternatives, simulate scenarios, inspect dependencies, and summarize structure. You decide the system's future costs and acceptable risks.

For growing engineers

Do not outsource the ability to read code. Learn by implementing, debugging, studying strong work, seeking mentorship, and building small things where mistakes are safe.

The transcript's practical rule is not “never use agents.” It is: understand the material the agent manipulates. A useful version for teams: junior engineers may use agents, but should be able to explain the feature path, altered data contract, test evidence, and failure mode without asking the agent again.

6. Product engineering: live in the technology and the customer's world

Martin defines a product engineer as someone who combines deep technical work with direct knowledge of the customer's real environment. A technically impressive solution without a felt problem is still weak product engineering.

Observe

See the work

Watch a customer complete the current task. Notice workarounds, interruptions, and information they must reconstruct.

Model

Turn pain into constraints

Define latency, trust, permissions, recoverability, and “must not make worse” conditions before implementation.

Validate

Check the outcome

After shipping, verify that users complete the job with less work—not merely that the feature is technically correct.

7. Deliberate practice: a 20-minute staff drill

  1. Choose a recent agent-generated feature or a pending request.
  2. Write one page: outcome, owner module, data flow, forbidden dependencies, failure/retry behavior, and evidence plan.
  3. Ask the agent for three failure paths your plan missed.
  4. Verify at least one objection against a real test, log, or code path.
  5. Write one customer assumption you still need to observe or confirm.

Pass condition: you can explain what changed in the system, why it belongs there, how it fails, and what proves it works. “The demo works” is not enough.

Transcript details retained

Architecture and the rising abstraction line
The interview frames the history of software as increasingly abstracted implementation: binary and assembly to high-level languages, and now agent-assisted coding. Its invariant is high-level design: modules, controlled dependencies, and information hiding.
Large systems and agents
Large systems remain composed of smaller systems. Agents can help with module-level work, reports, brainstorming, and simulations; people still compose the larger system and make cross-boundary choices.
Cleanliness, functions, comments, and tests
The interview relaxes some human-oriented micro-rules for agents, but keeps concern for function shape, names, argument counts, module structure, complexity, and strong tests. It treats comments as potentially more useful when agents maintain them.
Learning and product judgment
Design sense is presented as experience plus study, mentorship, curiosity, and hands-on play. Product engineering is presented as a union of technical competence and direct empathy with users' real work.
