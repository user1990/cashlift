The interview answer method

Do not dump everything you know. A strong answer is layered so the interviewer can stop or go deeper.

Concept question · 60–120 seconds

  1. Define the concept in one precise sentence.
  2. Mechanism: explain how it works.
  3. Example: use a small real production case.
  4. Trade-off: name the failure mode or boundary.
  5. Check: invite the interviewer deeper.

System question · Staff signal

  1. Clarify users, scale, constraints, and success.
  2. State assumptions and invariants.
  3. Sketch data flow and ownership boundaries.
  4. Choose trade-offs; reject alternatives explicitly.
  5. Cover failure, observability, rollout, and learning.

Communication

Say: “I’ll give the short model first, then show ordering with a code example. After that I can cover browser rendering or Node-specific differences.” This makes your thinking inspectable without turning the answer into a monologue.

General interview rules

  • Think aloud, but organize the thought: assumption → option → trade-off → decision.
  • Use a real example only when you can explain your exact contribution and outcome.
  • If uncertain, bound the uncertainty: “I believe X; I would verify it with Y.”
  • Never optimize before naming the measured bottleneck.
  • For Staff roles, connect local code choices to users, teams, operations, and long-term change cost.

JavaScriptMedium

1. Explain the JavaScript event loop

Short answer: JavaScript executes one job at a time on a call stack. Browser or runtime APIs perform asynchronous work; completed work schedules jobs. When the current stack is empty, the event loop runs queued work. Promise reactions use the microtask queue, which drains before the next task such as a timer or user event.

Call stack
Active execution contexts; synchronous calls push frames and returns pop them.
Runtime APIs
Timers, network, DOM events, and observers are provided by the host, not the ECMAScript language alone.
Microtasks
Promise reactions and queueMicrotask; drained after the current job before the next task.
Tasks
Timers, events, and other host work; one task runs, then microtasks drain, then rendering may occur.
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve()
  .then(() => console.log('C'))
  .then(() => console.log('D'));

queueMicrotask(() => console.log('E'));
console.log('F');

Predict the output.

Why C, E, then D?

The first then reaction and queueMicrotask are queued during the initial job. The second then is not queued until the first reaction resolves, so it is appended after E. The timer is a later task.

Harder follow-ups

  • Can microtasks starve rendering? Yes: continually scheduling microtasks can delay the next task and paint opportunity.
  • Does await block the thread? No. It suspends that async function; continuation is promise-driven.
  • What differs in Node.js? Its host phases and queues differ; never pretend the browser task model fully describes Node.
  • How would you diagnose a long task? Performance panel, long-task attribution, event timing/INP, and flame charts—not guesses.

Primary source: MDN JavaScript execution model.

JavaScriptMedium

2. What are closures?

Short answer: A closure is a function together with references to the lexical environment where it was created. The function can access those bindings later, even after the outer function returns.

function createCounter() {
  let count = 0;
  return {
    increment() { count += 1; },
    value() { return count; }
  };
}

const counter = createCounter();
counter.increment();
console.log(counter.value()); // 1

The closure captures the binding for count, not a frozen snapshot. This enables private state, factories, memoization, event handlers, and callbacks. It can also retain large objects longer than intended.

function attachHandlers(buttons) {
  for (var i = 0; i < buttons.length; i += 1) {
    buttons[i].onclick = () => console.log(i);
  }
}
// Every handler reads the same function-scoped binding.
// After the loop, that binding equals buttons.length.

React stale closure

useEffect(() => {
  const id = setInterval(() => {
    console.log(count); // reads the count from this Effect's render
  }, 1000);
  return () => clearInterval(id);
}, []); // count omitted: the Effect never re-synchronizes

The bug is not that closures are broken. The Effect intentionally retains values from the render that created it. Fix the synchronization model, not the symptom: include the dependency, use a functional updater, or restructure so the Effect does not need the changing value.

Replace var with let. What changes?

Harder follow-ups

  • What exactly is captured: values or bindings?
  • How do closures contribute to memory leaks?
  • Implement once, memoize, or debounce using a closure.
  • Explain stale closures in React without saying hooks are “async.”

Primary source: MDN Closures.

3. Difference between == and ===

Short answer: Strict equality (===) compares values without type coercion. Loose equality (==) follows the Abstract Equality Comparison algorithm and may convert operands before comparison. Prefer strict equality unless a deliberate coercion rule improves clarity.

ExpressionResultReason
0 == falsetrueBoolean converts to number.
0 === falsefalseTypes differ.
null == undefinedtrueSpecial loose-equality rule.
NaN === NaNfalseNaN is unequal to everything, including itself.
Object.is(NaN, NaN)trueSame-value semantics.
[] == ![]trueMultiple coercion steps; a reason to avoid cleverness.

Nuanced exception: value == null is a concise deliberate check for either null or undefined, with no other values matching. Use it only if the team recognizes the idiom.

What is [0 === '0', 0 == '0']?

Harder follow-ups

  • Compare ===, Object.is, and SameValueZero used by Map/Set.
  • Why does React compare hook dependencies using Object.is?

Short answer: “Hoisting” describes observable declaration-instantiation behavior; the engine does not literally move source lines. Function declarations are initialized with their function before execution. var bindings are created and initialized to undefined. let, const, and class bindings exist from scope entry but remain uninitialized in the temporal dead zone until evaluation reaches their declaration.

ReactMedium

5. What is the Virtual DOM?

Better answer: “Virtual DOM” is a popular shorthand for React representing desired UI as JavaScript element trees and reconciling successive renders. The precise model is trigger → render → commit. Rendering calls components to calculate UI; reconciliation determines necessary changes; commit applies them to the host DOM. A component rendering does not imply every corresponding DOM node changes.

Do not say: “The Virtual DOM is always faster than the real DOM.” React adds computation and memory. Its value is a declarative programming model plus efficient, predictable updates and scheduling—not a universal speed guarantee.

function SearchResults({ query, items }) {
  const visible = items.filter(item => item.name.includes(query));
  return visible.map(item => <Row key={item.id} item={item} />);
}

Keys tell React how child identity maps across renders. Stable domain IDs let state follow the logical item. Array indexes are unsafe when order can change, items can be inserted, or local state matters.

What does changing a component’s key do?

ReactMedium

6. useState vs useReducer

Short answer: Both store local component state and can express equivalent behavior. Use useState for simple, independent updates. Use useReducer when many events change related state, transitions have invariants, or centralizing pure transition logic improves readability, debugging, and testing.

type State =
  | { status: 'idle' }
  | { status: 'submitting' }
  | { status: 'success'; orderId: string }
  | { status: 'error'; message: string };

type Action =
  | { type: 'submitted' }
  | { type: 'succeeded'; orderId: string }
  | { type: 'failed'; message: string }
  | { type: 'retried' };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'submitted': return { status: 'submitting' };
    case 'succeeded': return { status: 'success', orderId: action.orderId };
    case 'failed': return { status: 'error', message: action.message };
    case 'retried': return { status: 'submitting' };
  }
}

The discriminated union prevents impossible combinations such as isLoading: true and isSuccess: true. The reducer must remain pure; network requests belong in event handlers, framework actions, or dedicated async/data layers.

Which is the better reducer candidate?

Staff lens

The decision is not “reducers scale.” Ask where state belongs, who owns the transition contract, how server state is synchronized, how URL state supports sharing, and whether a state machine or server-driven workflow is safer than adding more local state.

Harder follow-ups

  • How would you test the reducer without over-testing implementation?
  • Why must reducers be pure under Strict Mode and concurrent rendering?
  • When should state move to the URL, server cache, context, or external store?
  • How do you model optimistic updates and rollback?

Primary source: React: Extracting State Logic into a Reducer.

ReactHard

7. How does useEffect work?

Best mental model: An Effect synchronizes React state with an external system after commit. It is not a general-purpose “run after render” tool. Setup starts or updates synchronization; cleanup stops the previous synchronization. Every reactive value read by the Effect belongs in its dependency list.

useEffect(() => {
  const controller = new AbortController();

  loadProduct(productId, { signal: controller.signal })
    .then(setProduct)
    .catch(error => {
      if (error.name !== 'AbortError') report(error);
    });

  return () => controller.abort();
}, [productId]);
DependenciesMeaning
OmittedEffect runs after every commit.
[]No reactive dependencies; setup on mount and cleanup on unmount, plus development stress cycle.
[a, b]Re-synchronize when either differs by Object.is.

Cleanup timing: after a commit with changed dependencies, React first runs cleanup using old values, then setup using new values. On removal, cleanup runs once more. In development Strict Mode, React intentionally performs an extra setup → cleanup → setup cycle to expose broken symmetry.

Which usually does not need an Effect?

  • When should data fetching move to a framework or server-state library?
  • Explain useLayoutEffect and its paint trade-off.
  • How do Effect Events separate reactive synchronization from non-reactive reads?

CSSMedium

8. Flexbox vs CSS Grid

Short answer: Flexbox is primarily one-dimensional: distribute and align items along a row or column. Grid is two-dimensional: define rows and columns and place items against both. They compose; Grid often defines page or card structure while Flexbox aligns content inside a region.

Flexbox

.toolbar {
  display: flex;
  gap: .75rem;
  align-items: center;
}
.toolbar .search { flex: 1; }

The content and available space drive a single main axis.

Grid

.dashboard {
  display: grid;
  grid-template-columns:
    minmax(15rem, 1fr) 3fr;
  gap: 1rem;
}

The layout defines relationships across columns and rows.

Accessibility boundary: Visual reordering with Grid placement, Flexbox order, or reversed directions does not reliably change DOM, reading, or keyboard focus order. Start with meaningful source order.

Which is the strongest Grid use case?

Harder follow-ups

  • Explain intrinsic sizing, minmax(), auto-fit, and auto-fill.
  • Why does min-width: 0 fix some flex overflow bugs?
  • When does subgrid preserve semantic markup better than display: contents?
  • Design a container-query component rather than viewport-only breakpoints.

Primary sources: MDN Flexbox and Grid layout and accessibility.

JavaScriptHard

9. Promises and async/await

Short answer: A Promise represents the eventual fulfillment or rejection of an asynchronous result. async functions always return promises. await suspends that async function until the awaited value settles; it does not block the JavaScript thread. Continuation runs through promise jobs.

// Sequential: ~600 ms if each call takes ~300 ms
const user = await getUser();
const offers = await getOffers();

// Concurrent: ~300 ms when independent
const [user, offers] = await Promise.all([
  getUser(),
  getOffers()
]);
CombinatorUse when
Promise.allAll results required; reject fast on first rejection.
Promise.allSettledNeed every outcome, including failures.
Promise.raceNeed the first settled outcome.
Promise.anyNeed the first fulfillment; aggregate rejection if all fail.

Cancellation: Promises themselves are not generally cancellable. Cancel the underlying operation where supported, commonly with AbortController, and decide whether abort is an error, navigation, or expected supersession.

async function search(query, signal) {
  const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

How should independent requests usually run?

Staff lens

Concurrency is not automatically better. Consider rate limits, server load, priorities, streaming, cancellation, partial failure, backpressure, retry storms, idempotency, and whether the user benefits from progressive results.

Harder follow-ups

  • Explain promise resolution versus fulfillment.
  • What happens when a then callback returns a promise or throws?
  • Design retries with jitter, a budget, and idempotency.
  • Prevent autocomplete races, deduplicate requests, and cache safely.

Primary source: MDN async function.

Strong answer starts with measurement: define the affected user journey and metric, reproduce on representative devices and data, profile the bottleneck, fix the dominant cost, and verify user and business guardrails. “Add useMemo everywhere” is a red flag.

const ProductDetails = lazy(() => import('./ProductDetails'));

function ProductPage() {
  return (
    <Suspense fallback={<ProductSkeleton />}>
      <ProductDetails />
    </Suspense>
  );
}

Lazy loading trades initial JavaScript for later latency and loading-state complexity. Split at user-journey boundaries, preload likely next steps, handle chunk failures, and avoid fragmenting core UI into dozens of tiny requests.

What should happen before memoization?

Product + Staff lens

Build a performance operating model: real-user metrics by journey and device, performance budgets, ownership, release comparisons, alerting, and experiment-based links to conversion or retention. Make the fast path the default platform behavior, not a one-off heroic optimization.

Harder follow-ups

  • When can memo, useMemo, or useCallback
  • How do you distinguish render time, commit time, browser layout, and network latency?
  • Design a virtualization strategy that preserves keyboard and screen-reader usability.
  • How do React Compiler and server-first architectures change manual memoization choices?
  • How would you prove a performance change affected revenue?

Primary sources: React Render and Commit and web.dev code splitting.
