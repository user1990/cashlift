Think in failure modes

Your win: explain why payments and authentication demand more than correct happy-path UI.

  • 16 minutes
  • Systems judgment
  • Failure simulation

A critical journey is a state machine

A checkout does not simply “submit.” A payment can require a method, confirmation, additional authentication, asynchronous processing, success, cancellation, or another attempt. The interface must preserve truth across refreshes, redirects, retries, and delayed provider responses.

Risk = likelihood × consequence × detectability.

A rare duplicate charge deserves stronger prevention than a common cosmetic glitch because consequence is much higher. A silent analytics failure deserves attention because detectability is low.

Payment scenario

The browser times out immediately after confirmation. What should happen first?

Authentication scenario

A protected page disappears from navigation for unauthorized users. Is authorization complete?

Answer

No. Navigation is presentation, not enforcement. Server-side access control must protect the resource. Session lifecycle, logout invalidation, sensitive-operation re-authentication, error logging, and recovery flows are separate concerns. OWASP ASVS organizes these into explicit verification areas.

Practical drill

Choose a journey you owned. List one failure before submission, one during an external handoff, and one after apparent success. For each, name the authoritative state and the user-safe recovery.

Before: expired price → pricing service → refresh quote without losing cart.

During: 3DS return missing → payment provider → resume or safely retry from intent status.

After: receipt API delayed → order service → show pending state and poll/reconcile, never create a second order.

Primary reading: Stripe PaymentIntent lifecycle. For identity controls, use the OWASP ASVS.
